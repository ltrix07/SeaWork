## Принятые решения, определившие этот список

- **Веха 2 — расширение источников.** Цель ближайшего периода — полнота и качество данных, а не видимый прототип.

- **LLM-обогащение измерено 22.09.2026.** Обогатитель, оценка и выбор модели сделаны; порог по ложным заполнениям взят. Открытым остался второй провайдер (D3) и повторяемость замера (D4).

**Известная цена выбранного порядка.** Эталон в `tests/fixtures/eval/enrichment_gold.yaml` собран на трёх источниках (75 записей после D0). Каждый новый источник делает его менее представительным и требует примерно часа доразметки — счёт по PADI ещё не оплачен, см. остаток в D0.

- [x] **D0. Доразметка эталона под новые источники** · выполнено 26.07.2026
  Эталон вырос с 50 записей до **75**: 29 Crewplanet, 25 Princess, 21 Holland America.
  Princess-слой размечен вручную, как и исходный: разметить моделью — значит измерить согласие модели с самой собой, а не её точность.

- [x] **D1. `LLMEnricher`** · выполнено 26.07.2026
  Два поля, до которых не достают правила: `experience_level` и `required_certificates`.
  Провайдер задаётся конфигурацией (`SEAWORK_LLM_*`), а не выбирается в коде — один OpenAI-совместимый слой со structured output.
  Модель обязана вернуть цитату-обоснование на каждое заполненное поле: цитата, которой нет в исходном тексте, и есть детектор выдумок для §7 спеки.
  Правила имеют приоритет: LLM дополняет только пустые поля и никогда не перезаписывает найденное правилом.
  Без настроенного провайдера `ingest run` работает как раньше — fail-open, а не падение.
  Сверх спеки сделано: персистентный кэш в основной БД (миграция `0002_llm_cache`, ключ `content_hash` × `prompt_version` × `model_id`) — переживает `reprocess` в новом процессе; ретраи с экспоненциальным backoff и уважением `Retry-After`, с потолком в 60 с, чтобы чужой заголовок не подвесил загрузку.
  **Batch-режим отменён осознанно** (§6 спеки): `enrich()` вызывается по одной записи, batch требует двухфазного пути и не унифицирован между провайдерами, а выигрыш −50% относится к расходу, признанному незначимым в `docs/ai-cost-boundary.md` §7.

- [x] **D2. `seawork eval enrichment`** · выполнено 26.07.2026
  Метрики по каждому полю против эталона, плюс `--show-errors` — поимённый разбор расхождений.
  Разбор добавлен не для удобства: урок B6 в том, что доля заполнения без проверки каждого совпадения поимённо — обманчивая цифра.

- [~] **D3. Прогон моделей и выбор** · измерено 22.09.2026 · осталось подтвердить второго провайдера
  Прогнано 9 раз на эталоне из 75 записей, OpenAI, модели `gpt-5.4-mini` и `gpt-4.1-mini`. Один прогон — 75 вызовов, 1м13с, центы.

  **Порог взят по обоим полям на обеих моделях:**

  | Поле | gpt-5.4-mini | gpt-4.1-mini | порог |
  |---|---:|---:|---:|
  | Опыт: ложные заполнения | 1.3% | 1.3% | ≤5% |
  | Сертификаты: ложные заполнения | 1.3% | 0.0% | ≤5% |
  | Опыт: точность / полнота | 86.3% / 84.6% | 90.9% / 76.9% | |
  | Сертификаты: точность / полнота | 63.6% / 63.6% | 70.0% / 63.6% | |
  | **Невалидные цитаты** | **0.0%** | **8.3%** | |

  **Выбор — `gpt-5.4-mini`.** Решает не точность, а последняя строка: `gpt-4.1-mini` выдумывает цитаты в каждом прогоне, `gpt-5.4-mini` не выдумал ни одной за шесть. Объяснимость Match Score (SPEC.md §10.7) держится на цитате, и модель, которая её сочиняет, не годится, даже когда её агрегаты выше.

  **Чем взят порог — не промптом.** Две правки промпта дали 8.0% → 6.7% → 8.0%, то есть ничего: это разброс в одну запись. Порог взяла проверка ключа по паттернам справочника (`quote_names_certificate`). Все ложные заполнения были подменой ключа при настоящей цитате, и это ловится механически, без веры в послушание модели.

  **Измеренная цена:** полнота по сертификатам 90.9% → 63.6%. Причина — пробел в справочнике, а не фильтр: эталонная цитата «medical fitness check» не совпадает ни с одним паттерном `marine_medical`. Лечится данными (задача C4), и правила-обогатитель слеп к этой формулировке ровно так же.

  *Остаток:* спека требует минимум двух **провайдеров**, а прогнаны две модели одного. Доступа ко второй платформе на 22.09.2026 не было. Провайдер-независимость подтверждена архитектурно (клиент конфигурируемый), но не измерением.

- [ ] **D4. Замер разброса и повторяемость** · S · после D3
  Одиночный прогон не различает эффекты, которые мы пытаемся читать: на 75 записях одна запись весит 1.3 пункта, а два прогона одной модели при `temperature=0` дали точность по сертификатам 58.8% и 52.6%. Температура убрала разброс по опыту и не убрала по сертификатам.
  Любое решение по промпту принимать по 3–5 прогонам со средним и размахом, а не по одному числу.

## Порядок и зависимости

```
D0 ✓ → D1 ✓ → D2 ✓ → D3 ~ → D4 → C3, C4

A1 → A2 → A3 ──────────┐
                       ├──→ B2 ──→ доразметка PADI в эталоне
B3 ✓ → B4 ✓ → B6 ✓ ────┘
C1, C2, B5, B10 — параллельно, ни от чего не зависят
```

**B1 выпала из цепочки:** источника с JSON-LD не нашлось, и B2 больше от неё не зависит.

**B3 выполнена и уже изменила план:** нашла Princess Cruises (+354 вакансии) и одновременно показала, что подключение стоит дороже строчки в реестре — отсюда пересмотр B4 и новая задача B6.

**Дальше — C4 и D4.** D3 показала, что потолок теперь не в модели: ложные заполнения сбиты до 0–1.3%, а полноту держит справочник. C4 поднимает её данными, D4 делает замер повторяемым, чтобы следующие решения принимались не по одному прогону.

Параллельно — **C2**: риск повторения дефекта с потерей данных ничем не закрыт, а скрипты для его отлова уже написаны и просто не вызываются.

**Ответ на вопрос вехи 1** — хватает ли качества данных для матчинга — стал измеримым: по опыту и сертификатам модель не выдумывает (0% невалидных цитат, ложные заполнения 1.3%), но и не заполняет всё. Полнота, а не достоверность, теперь главный ограничитель.
