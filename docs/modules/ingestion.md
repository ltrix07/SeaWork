# Модуль: Ingestion (парсер + нормализация)

> Статус: спроектирован, не реализован
> Соответствует SPEC.md, разделы 4 (Career Opportunities Model) и 9.3–9.7 (Recommendation Pipeline, этапы 1–5)

---

## 1. Контекст

Sea Work — карьерная платформа для морской индустрии. Ключевая идея продукта: система не показывает поток вакансий, а отбирает для пользователя единичные действительно полезные **карьерные возможности** (`CareerOpportunity`). Отбор делает Recommendation Engine на основе `Match Score` — числовой оценки соответствия возможности конкретному пользователю.

**Ingestion — первый модуль системы.** Он превращает разрозненные внешние источники в единый поток нормализованных `CareerOpportunity`.

Полный пайплайн из SPEC.md выглядит так:

```
Источник → Нормализация → Проверка качества → Определение типа →
Обогащение → Match Score → Подписка → История → Группировка →
Рекомендация → Delivery
```

**Этот модуль реализует только первые пять этапов.** Всё, что начинается с Match Score, — вне рамок.

### 1.1 Главная цель первой итерации

Не «собрать много вакансий». Цель — **измеримо ответить на вопрос: можно ли вообще построить Match Score на реальных данных.**

Match Score считается по полям `profession`, `direction`, `country`, `required_certificates`, `experience_level`. Если реальные источники эти поля не отдают и их нельзя надёжно вывести — вся продуктовая концепция требует пересмотра (например, обязательной LLM-экстракции с соответствующей стоимостью).

Поэтому **обязательным артефактом модуля является отчёт о заполняемости полей** (см. §8). Это не опция и не «приятное дополнение» — это основной результат работы.

## 2. Границы модуля

### Входит

- Получение данных из внешнего источника
- Сохранение сырого ответа (raw payload)
- Нормализация в единую доменную модель
- Проверка качества и отбраковка мусора
- Определение типа `CareerOpportunity`
- Детерминированное обогащение (правила, справочники)
- Дедупликация и отслеживание изменений
- Отчёт о заполняемости полей

### Не входит (не реализовывать)

- Match Score и любая персонализация
- Telegram-бот, любой UI
- Delivery Engine, отправка уведомлений
- Модель пользователя, подписки
- LLM-обогащение (интерфейс закладываем, реализацию — нет)
- Более одного источника
- Планировщик/крон (запуск только вручную через CLI)

## 3. Ключевые архитектурные решения

Эти решения обязательны к соблюдению. Если реализация вынуждает их нарушить — остановиться и вынести вопрос на обсуждение, а не обходить.

### 3.1 Сырой payload сохраняется всегда

Каждый полученный ответ источника сохраняется в БД до нормализации.

Причина: правила нормализации и обогащения будут переписываться десятки раз. Без сохранённого payload каждая правка требует повторного обхода сайта — это медленно, создаёт нагрузку на источник и повышает риск бана. С сохранённым payload перенормализация всей базы — локальная операция на несколько секунд.

Следствие: `normalize` и `enrich` обязаны быть работоспособны **полностью офлайн**, на данных из БД, без сетевых вызовов.

### 3.2 Нормализация не имеет права додумывать

Этап нормализации переносит **только то, что источник сообщил буквально**. Если в вакансии не указана страна — поле остаётся `None`. Запрещено угадывать страну по названию работодателя, домену или языку текста.

Любой вывод, догадка, извлечение из свободного текста — это **этап обогащения**, отдельный и последующий.

Причина: SPEC.md §10.7 требует объяснимого Match Score — система показывает пользователю, *почему* рекомендация подходит («не требует дополнительных сертификатов», «в интересующей вас стране»). Объяснение, построенное на догадке, выданной за факт источника, — это ложь пользователю и прямой удар по доверию, которое SPEC.md §8.8 называет стратегической целью продукта.

### 3.3 Каждое выведенное поле несёт происхождение и уверенность

Обогащённые поля хранятся не как голые значения, а вместе с метаданными:

```python
class Provenance(StrEnum):
    SOURCE = "source"   # источник сообщил явно
    RULE   = "rule"     # выведено детерминированным правилом
    LLM    = "llm"      # выведено моделью (пока не реализовано)

class Inferred[T](BaseModel):
    value: T
    provenance: Provenance
    confidence: float  # 0.0–1.0; для SOURCE всегда 1.0
```

Match Score в дальнейшем сможет взвешивать факты по достоверности, а объяснения — ссылаться только на то, что действительно известно.

**Ненайденное — это `None`, а не пустое значение.**

Если правило отработало и ничего не нашло, поле обязано остаться `None`. Записывать `Inferred(value=[], provenance=RULE, confidence=0.9)` запрещено: пустой список с высокой уверенностью читается как «правило установило, что требований нет», тогда как на деле это «наши шаблоны ничего не распознали».

Разница не academic. Match Score, увидев `required_certificates = []` с `confidence=0.9`, вправе построить объяснение «не требует дополнительных сертификатов» (SPEC.md §10.7) — то есть уверенно сообщить пользователю ложь и повлиять на его решение о деньгах и времени. Это тот же принцип §3.2, но этажом выше: не додумывает не только нормализация, но и обогащение.

Поэтому все поля `Inferred[...]` объявляются опциональными без исключений.

### 3.4 Этапы — чистые функции

`normalize`, `check_quality`, `classify`, `enrich` не ходят в сеть и не пишут в БД. Сигнатура вида «на входе объект, на выходе объект». Ввод-вывод сосредоточен в `pipeline.py` и слое storage.

Причина: тестируемость. Основной риск парсера — тихая деградация при изменении вёрстки источника, и ловится он только тестами на зафиксированных фикстурах.

### 3.5 Источник изолирован за интерфейсом

Вся логика, специфичная для конкретного сайта, живёт внутри `sources/<name>/` и не протекает наружу. Ядро пайплайна не знает названий источников.

Причина: SPEC.md §4.9 требует, чтобы добавление новых типов возможностей и источников не меняло бизнес-логику.

### 3.6 Идемпотентность

Повторный запуск на тех же данных не создаёт дубликатов и не ломает состояние. Ключ уникальности — `(source_id, external_id)`. Изменение содержимого отслеживается через `content_hash`.

## 4. Доменная модель

Типы возможностей — по SPEC.md §4.3:

```python
class OpportunityType(StrEnum):
    JOB = "job"
    INTERNSHIP = "internship"
    VOLUNTEER = "volunteer"
    COURSE = "course"
    CERTIFICATION = "certification"
    ARTICLE = "article"
    NEWS = "news"
    RESEARCH = "research"
    EVENT = "event"
```

### 4.1 RawItem — результат этапа 1

```python
class RawItem(BaseModel):
    source_id: str          # "example-source"
    external_id: str        # идентификатор внутри источника
    url: str
    fetched_at: datetime
    payload: str            # HTML или JSON как есть
    content_type: str       # "text/html" | "application/json"
    content_hash: str       # sha256 от payload
    http_status: int
```

### 4.2 NormalizedOpportunity — результат этапа 2

Только буквальные данные источника. Почти всё опционально — отсутствие поля это нормальный, ожидаемый случай.

```python
class NormalizedOpportunity(BaseModel):
    source_id: str
    external_id: str
    url: str

    title: str                          # единственное обязательное поле
    description: str | None             # текст, HTML вычищен
    employer: str | None

    location_raw: str | None            # строка как в источнике
    salary_raw: str | None
    posted_at: datetime | None

    declared_type: str | None           # категория источника, если есть
    language: str | None                # определён детектором, не угадан
```

### 4.3 EnrichedOpportunity — результат этапов 3–5

```python
class EnrichedOpportunity(BaseModel):
    normalized: NormalizedOpportunity

    type: OpportunityType
    type_confidence: float

    country: Inferred[str] | None            # ISO 3166-1 alpha-2, берег
    city: Inferred[str] | None               # берег
    embarkation_port: Inferred[str] | None   # ключ из ports.yaml, судно
    operating_region: Inferred[str] | None   # ключ из regions.yaml, судно
    profession: Inferred[str] | None         # из справочника профессий
    direction: Inferred[str] | None          # дайвинг/яхты/наука/круизы/...
    required_certificates: Inferred[list[str]] | None
    required_languages: Inferred[list[str]] | None
    preferred_languages: Inferred[list[str]] | None
    experience_level: Inferred[ExperienceLevel] | None
    salary: Inferred[SalaryRange] | None
    workplace_type_hint: Inferred[str] | None

    quality_score: float
    quality_flags: list[str]
```

Справочники профессий, направлений и сертификатов — YAML-файлы в `data/reference/`. Не хардкодить в Python: их будет править человек с доменной экспертизой, а не разработчик.

### 4.3.1 География: четыре поля вместо двух

**Задача A1. Решено 22.09.2026.**

У судового контракта нет страны работы в береговом смысле. Это не дефект парсинга: все три подключённых источника дают `country` в 0% случаев, и так будет с любым судовым источником. Судно перемещается, а наниматель называет не страну, а **порт посадки** («join in Barcelona») и **регион работы** («Caribbean season», «North Sea»).

Поэтому вводятся два поля, и именно два, а не одно:

- **`embarkation_port`** — куда человек физически прилетает на посадку. Определяет стоимость и визы.
- **`operating_region`** — где судно ходит. Определяет климат, длину контракта, связь, характер работы.

Смешивать их нельзя: посадка в Барселоне бывает и у средиземноморского, и у трансатлантического рейса, а это для моряка разные контракты.

**Почему не `embarkation_port_raw`,** как задача называлась в роадмапе. В этом коде суффикс `_raw` значит «строка ровно как её написал источник», такие поля живут в `NormalizedOpportunity` и не несут происхождения — `location_raw`, `salary_raw`, `recruitment_office_raw`. Поле типа `Inferred[...]` по определению выведено и несёт `provenance` с `confidence`. Имя `embarkation_port_raw: Inferred[str]` утверждало бы обе вещи разом. Значение нормализуется до ключа справочника, как `profession` и `direction`, и потому суффикс снят.

**Старые поля не удаляются.** `country` и `city` остаются и остаются пустыми у судовых источников. Удалить их означало бы закрыть дорогу береговым вакансиям, которые спека предполагает (`SPEC.md` §4), и потерять единственное место, куда такой источник положит своё место работы.

**Схема общая, а не две ветки** — второй открытый вопрос задачи A1. Все четыре поля допускают `None`, и судовая вакансия просто не заполняет береговые, а береговая — судовые. Причины:

1. Развилка типов расщепила бы все пять этапов конвейера ради двух полей.
2. Поля **не взаимоисключающие**: у offshore-вакансии бывает и страна базы, и порт мобилизации.
3. Различать случаи уже есть чем — `workplace_type_hint`; заводить для этого второй механизм незачем.

Match Score выбирает, что спрашивать у пользователя, по заполненности полей, а не по типу записи. Отсутствие географии — это `None`, а не ноль: «регион неизвестен» и «регион не подходит» обязаны различаться, иначе фильтр будет молча выбрасывать вакансии, о которых мы просто ничего не знаем.

**Ожидания по заполняемости низкие и это нормально.** У Crewplanet есть поле `Location`, у Pinpoint — только офис найма, который уже отделён в `recruitment_office_raw` именно затем, чтобы не выдать себя за место работы. Реальные цифры даёт A3; по ним же решается, нужен ли здесь LLM.

## 5. Этапы

### 5.0 Классификация источников

Источники подключаются в порядке убывания структурности данных:

| Уровень | Тип | Ожидаемое качество |
|---|---|---|
| 1 | Открытый API / RSS | поля типизированы, `provenance=SOURCE` |
| 2 | Полуоткрытый API (внутренние запросы страницы) | обычно богаче RSS, полная запись |
| 3 | Платный API | если экономически оправдан |
| 4 | HTML-скрапинг | поля выводятся правилами, `provenance=RULE` |

Приоритет обусловлен не трудозатратами, а §1.1: чем выше уровень, тем больше полей приходит как факт источника, а не как догадка, и тем выше шанс, что Match Score строится без LLM.

**Проверка 1 — ATS-платформа.** Определить, на какой системе управления наймом работает сайт (отпечатки в HTML: `pinpointhq`, `workable`, `teamtailor`, `greenhouse`, `lever`, `recruitee`, `myworkdayjobs`, …). У большинства из них есть публичный JSON API без авторизации — им питается виджет вакансий на сайте клиента. Это сразу уровень 1.

**Проверка 2 — JSON-LD.** На карточке вакансии искать `<script type="application/ld+json">` со схемой `schema.org/JobPosting`. Разметка распространена, поскольку требуется для индексации в Google Jobs, и содержит `title`, `hiringOrganization`, `jobLocation`, `baseSalary`, `employmentType`, `datePosted`, `validThrough`, `qualifications`. При её наличии сайт поднимается до уровня 1 независимо от отсутствия API.

### 5.0.2 Адаптер пишется под платформу, а не под сайт

Ключевое следствие разведки (`docs/sources-research.md`): один адаптер Pinpoint открывает всех работодателей на Pinpoint, включая тех, кого подключат позже. Проверено на практике — один эндпоинт Holland America отдаёт вакансии сразу трёх круизных брендов Carnival.

Поэтому директории источников делятся на два вида:

```
sources/
├── platforms/          # переиспользуемые: pinpoint, workable, teamtailor, jsonld
└── sites/              # индивидуальные, когда платформу определить не удалось
```

Подключение работодателя на уже поддержанной платформе должно сводиться к **строке в конфигурации** — идентификатор аккаунта и `source_trust`, — а не к новому коду.

Оговорки по уровню 2: у внутренних API нет контракта и они могут измениться без предупреждения; перед подключением проверять условия использования сайта и не обходить намеренно выставленную защиту.

### 5.0.1 Source trust

Уровень источника описывает **структурность** данных. Отдельно и независимо от него задаётся `source_trust` — **достоверность** содержимого:

```python
class SourceTrust(StrEnum):
    PRIMARY    = "primary"      # первичные вакансии от нанимателя/площадки
    AGGREGATED = "aggregated"   # перепечатка из других источников
    UNTRUSTED  = "untrusted"    # машинно-сгенерированный или непроверяемый контент
```

Задаётся вручную в конфигурации источника, не выводится автоматически.

Причина введения: разведка (см. `docs/sources-research.md`) обнаружила источник с технически образцовым RSS, где все записи помечены самим сайтом как AI-сгенерированные, работодателями значатся агрегаторы, а локации имеют вид `Worldwide`. Хорошая доставляемость данных не равна их пригодности.

Правило: объекты с `UNTRUSTED` проходят весь пайплайн и попадают в базу, но **не могут быть выданы пользователю**. Они нужны для отладки, метрик и сравнения покрытия — SPEC.md §8.8 делает доверие пользователя стратегической целью, и одна машинная выдумка в ленте стоит дороже, чем сотня недостающих вакансий.

Отчёт §8 строится **по каждому `source_trust` отдельно** — иначе мусорный источник исказит статистику заполняемости, ради которой писался модуль.

### Этап 1 — Fetch

Реализация `Source` для конкретного источника.

```python
class Source(Protocol):
    source_id: str
    tier: SourceTier

    def collect(self, since: datetime | None = None) -> AsyncIterator[RawItem]: ...
```

Единый метод вместо пары `discover`/`fetch`: у источников уровня 1–2 один HTTP-запрос возвращает страницу с десятками объектов сразу, и разбиение на «получить URL» + «скачать по URL» для них неестественно. Стратегию выбирает сам источник, ядро пайплайна получает единый поток `RawItem`.

Предоставляются два базовых класса:

- **`BulkSource`** — для API и RSS: пагинация, много `RawItem` из одного ответа. Если источник поддерживает `updated_since`, использовать его для инкрементального обхода.
- **`ListDetailSource`** — для HTML и для связки «RSS как обнаружение + страница как детали»: обход списка, затем запрос каждого объекта. Останавливается, встретив N подряд известных `external_id`.

Требования к обоим:
- rate limit, по умолчанию не чаще 1 запроса в секунду, настраивается на источник
- ретраи с экспоненциальной задержкой на 5xx и таймауты; на 4xx ретраев нет
- честный User-Agent с контактом, без маскировки под браузер
- соблюдение `robots.txt` — проверять перед обходом, при запрете прекращать работу с логированием

### Этап 2 — Normalize

`RawItem → NormalizedOpportunity`. Соблюдать §3.2 — никаких догадок.

Практика: держать разбор HTML (`parser.py`, «где что лежит на странице») отдельно от маппинга в домен (`mapper.py`, «как это ложится в модель»). При смене вёрстки правится только первый файл.

### Этап 3 — Quality gate

Отбраковка до персонализации. Объект отклоняется, если:
- пустой или мусорный `title`
- нет `url` или он не резолвится
- `description` короче 100 символов
- дубликат по `content_hash` внутри того же источника

Отклонённые объекты **сохраняются с флагом**, а не удаляются: по ним считается статистика качества источника. Каждое отклонение логируется с причиной.

### Этап 4 — Classify

Определение `OpportunityType`. Порядок приоритета:
1. `declared_type` источника, если он есть и однозначно мапится
2. правила по ключевым словам в `title` (`internship`, `volunteer`, `course`, …)
3. фолбэк `JOB` с `type_confidence = 0.5`

Без ML. Правила — в YAML.

### Этап 5 — Enrich

Детерминированное обогащение:
- `country` — из `location_raw` через справочник стран и городов
- `profession`, `direction` — сопоставление `title` со справочником
- `required_certificates` — поиск известных сертификатов в тексте (PADI, SSI, IMCA, HSE, STCW, …)
- `experience_level` — правила по формулировкам («no experience», «5+ years»)
- `salary` — разбор `salary_raw` в диапазон с валютой и периодом

Каждое поле — `Inferred[...]` с `provenance=RULE` и осмысленной `confidence`. Поле, которое правило не смогло вывести, остаётся `None`. **Заполнять поля значениями-заглушками запрещено** — это исказит отчёт §8, ради которого модуль и пишется.

Интерфейс `Enricher` спроектировать так, чтобы LLM-обогатитель позже подключался как ещё одна реализация без изменения пайплайна.

## 7. Хранилище

Две таблицы.

**`raw_items`** — сырые ответы.
`id`, `source_id`, `external_id`, `url`, `fetched_at`, `payload` (TEXT), `content_hash`, `http_status`
Уникальный индекс: `(source_id, external_id, content_hash)`

**`opportunities`** — обработанные объекты.
`id`, `raw_item_id` (FK), `source_id`, `external_id`, `url`, `title`, `description`, `employer`, `type`, `type_confidence`, `enriched` (JSONB — все `Inferred`-поля), `quality_score`, `quality_flags` (JSONB), `status` (`active` | `rejected`), `created_at`, `updated_at`
Уникальный индекс: `(source_id, external_id)`

Обогащённые поля лежат в JSONB намеренно: их состав будет активно меняться на протяжении нескольких итераций, и гонять миграцию на каждое новое поле — лишнее трение. Как только состав стабилизируется, ключевые поля выносятся в колонки.

### 7.1 Образ Postgres

Использовать образ `pgvector/pgvector:pg16`, но **расширение пока не включать и таблицу эмбеддингов не создавать**.

Причина: на следующих вехах эмбеддинги понадобятся сразу для трёх задач — Interest Vector (SPEC §7.4), семантическая близость в Match Score и группировка похожих вакансий (SPEC §9.11). Взять сразу нужный образ стоит ноль усилий и избавляет от смены базового образа в проде позже. Заводить саму векторную инфраструктуру до появления этих задач — преждевременно.

## 9. Тестирование

Основной риск парсера — тихая поломка при смене вёрстки источника. Отсюда:

- В `tests/fixtures/<source>/` кладутся **реальные сохранённые HTML-страницы** (не менее 10, включая заведомо проблемные: без зарплаты, без локации, с нестандартной вёрсткой)
- Тесты парсера гоняются офлайн, только на фикстурах, без сети
- Сетевой слой тестируется через `respx` с замоканными ответами
- Правила обогащения покрываются табличными тестами: строка на входе — ожидаемый `Inferred` на выходе
- `pyright` в strict-режиме проходит на всём `src/`

### 9.1 CI

С первого коммита — GitHub Actions на каждый push и PR: `ruff check`, `ruff format --check`, `pyright`, `pytest`, сборка Docker-образа, проверка что миграции накатываются на чистую БД.

Причина: код пишет Codex, ревьюит человек. Автоматические ворота качества — единственное, что надёжно ловит регрессии в парсере до того, как они попадут в базу.
