# Модуль: Recommendation Engine

> Этапы 7–10 конвейера (`SPEC.md` §9.9–9.12) в объёме, нужном для запуска бота. Продуктовый замысел — `SPEC.md` §8. Зависит от `docs/modules/user-profile.md` и `docs/modules/match-score.md`. Карта кода — `docs/plans/bot-launch/map.md`.
>
> Написано 12.10.2026.

---

## 1. Контекст

Match Score отвечает «насколько эта вакансия подходит этому человеку». Recommendation Engine отвечает на другой вопрос (§8.1):

> Что именно необходимо показать этому пользователю именно сейчас?

Сейчас в коде нет ничего, что выбирает. Оценка считается только в тестах, вакансии из базы никто не читает, показанное нигде не запоминается. Бот без этого модуля либо будет выбирать сам — и бизнес-логика окажется в клиенте, что запрещает §1.5, — либо будет присылать одно и то же.

Главное требование спеки — доверие, а не объём (§8.8, §9.13): «лучше не показать объект вовсе, чем показать нерелевантную рекомендацию», «лучше отправить меньше качественных рекомендаций, чем больше посредственных» (§3).

## 2. Границы модуля

### Входит

- выбор и упорядочивание рекомендаций для одного пользователя из набора кандидатов;
- исключение по истории: показанное и отклонённое;
- группировка похожих вакансий в одну карточку (§9.11);
- разнообразие по направлениям (§5.4, §5.5);
- лимит размера подборки без добивания до лимита;
- хранилище истории выдачи (`deliveries`) и чтение кандидатов из базы — как опора для движка.

### Не входит (не реализовывать)

- **отправка сообщений и расписание** — Delivery Engine (§8.5, §9.12); в нашем проекте это слой бота и команда рассылки, отдельная спека;
- **тарифы**: в v1 все пользователи на FREE, лимит — параметр вызова (§9.9 «подписка не влияет на Match Score» — и на выбор тоже не влияет, только на число);
- **вывод интересов и смена Stage по поведению** — Feedback Engine (§8.5, §6.10), `user-profile.md` §6.1 ждёт замера после запуска;
- **нетипичные объекты** (статьи, истории, новости из §4.7 и §6.3): в корпусе их нет, только вакансии и стажировки;
- **повторный показ** при оценке выше ~85% (§9.10): порог не значит ничего до калибровки весов (`match-score.md` §6.3), см. §3.4;
- AI-формулировка объяснения — объяснение берётся из `MatchScore.verdicts` как есть.

## 3. Ключевые архитектурные решения

### 3.1 Движок — чистая функция, загрузка снаружи

`recommend()` получает профиль, кандидатов и историю уже собранными и ничего не читает сам. Так же устроен Match Score, и по той же причине: всю логику выбора можно проверить тестами без базы, а у бота, рассылки и будущего Mini App один и тот же код решения (§1.5 «одинаковые алгоритмы независимо от способа взаимодействия»).

Сборку входов делает сервисный слой, который вызывает бот. Он в этот модуль не входит, но его единственная работа — прочитать три вещи и передать их сюда.

### 3.2 Кандидат — активная, неснятая вакансия

В выдачу попадают записи со `status = active`, кроме:

- **снятых с источника** — понятие вводится отдельным шагом плана (вакансия исчезла из полной выдачи источника). Сегодня исчезнувшая вакансия остаётся `active` навсегда, и для запуска это худший возможный дефект: приглашение на закрытую вакансию разрушает ровно то доверие, на котором стоит §8.8;
- **с пометкой `source_trashed`** (17 записей PADI). Пометка намеренно не отклоняет запись в корпусе (`padi.py`, `quality_notes`) — и это верно для корпуса. Но выдача — другой вопрос: пост в корзине чужой CMS — сильный признак, что вакансию сняли, а показывать сомнительное хуже, чем не показать (§9.13). Исключение действует только в выдаче. · *подтверждено 12.10.2026*

Тип возможности не фильтруется: и `job`, и `internship` идут в одну ленту.

### 3.3 Отказ — навсегда, пока человек его не отменит

`dismissed` исключает вакансию из выдачи без срока. Отменяет его только событие `reopened`, записанное **позже**: для каждой вакансии побеждает последнее из двух. Это закрывает вопрос «отменяемость `dismissed`» из `user-profile.md` без правки журнала, который остаётся append-only.

«Не отреагировал» — не отказ. Спека их различает (§9.10 «проигнорировал» и кнопка «Не интересно»), и смешивать нельзя: молчание в Telegram бывает просто непрочитанным сообщением.

### 3.4 Показанное не повторяется

В v1 вакансия, однажды доставленная пользователю — сама или как участник группы, — больше не попадает в его выдачу. §9.10 разрешает повтор при оценке «примерно выше 85%», но до E2.1 одна и та же вакансия набирает 70% или 95% в зависимости от произвольных весов, и правило свелось бы к случайности. Вернуться после калибровки.

История выдачи — **отдельная таблица `deliveries`, а не действие в журнале поведения**. Журнал записывает, что сделал человек; доставку совершила система. Смешать их значит заставить `interest_counts` и будущий Feedback Engine различать «человек посмотрел» и «мы прислали» по типу события в каждом запросе, а `BehaviourAction` по карте нельзя расширять без пересмотра счётчиков.

### 3.5 Полный промах не показывается

Кандидат с `value == 0.0` исключается: все сравнимые факторы — промахи. Это пример из §6.8 — новичку вакансия с пятью годами опыта. Это не жёсткий фильтр в смысле `match-score.md` §3.3: тот запрещает выбрасывать по **неизвестному**, а здесь выбрасывается то, про что известно, что не подходит ничем.

Других порогов нет. Любое число между 0 и 1 до E2.1 — выдумка.

### 3.6 Порядок: оценка, затем доказанность, затем свежесть

Ключ сортировки, по убыванию:

1. есть ли оценка (`value is not None`) — вакансия, про которую что-то известно, идёт раньше той, про которую неизвестно ничего;
2. `value`;
3. `comparable_factors` — 80% по четырём факторам сильнее 80% по одному (`match-score.md` §3.2);
4. свежесть: `posted_at`, а где его нет — `first_seen_at` (Pinpoint дату не отдаёт, `posted_at` есть у ~26%);
5. `opportunity_id` — для детерминизма.

Пункт 1 — решение v1, а не истина: не ясно, лучше ли 0.3 по фактам, чем полная неизвестность. Ответит эталон E2.1.

### 3.7 Похожие вакансии — одна карточка

§9.11: «пользователь видит одну карточку» с пометкой «ещё найдено N похожих». Ключ группы — пара **(работодатель, профессия)** после нормализации регистра и пробелов. Princess Cruises публикует одну и ту же должность под разные суда десятками; это одна возможность, а не тридцать.

- Группируется только кандидат, у которого известны **оба** поля. Без профессии или работодателя запись — сама себе группа: склеить по неизвестному значит выдумать сходство.
- Представитель группы — лучший по §3.6. Остальные уходят в `similar_ids` и записываются в `deliveries` вместе с ним: показывать их потом по одному значит повторить ту же возможность.
- Группировка выполняется **до** лимита: группа занимает одно место.

### 3.8 Разнообразие по направлениям

§5.4 запрещает «десять подряд вакансий только по коммерческому дайвингу», §5.5 делает смешанную выдачу сценарием для «не определился». После сортировки и группировки подборка собирается по кругу: представители раскладываются по корзинам `direction`, корзины упорядочиваются по своему лучшему элементу, и из них берётся по одному, пока не набран лимит. Без направления — своя корзина.

Это не фильтр: направления, которые человек назвал, уже подняты фактором `direction` в оценке, а круг лишь не даёт одной корзине занять всю подборку.

### 3.9 Лимит без добивания

`limit` — параметр (по умолчанию для ежедневной подборки — 5, §3 «до пяти карьерных возможностей», период в спеке не назван, принимаем «в день»). Если прошло меньше кандидатов, возвращается меньше; пустой список — нормальный ответ, а не ошибка. Что сказать человеку при пустой подборке — забота бота.

### 3.10 Холодный старт

У пустого профиля `value is None` для всех вакансий (`match-score.md` §4). Движок не придумывает оценку: порядок определяют свежесть и круг по направлениям. Значит, все новые пользователи без ответов в один день видят одинаковую подборку — разнообразную, свежую и без промахов. Для v1 это честнее, чем ранжировать по случайности, и это сказано вслух.

## 4. Доменная модель

`src/seawork/domain/recommendation.py`, frozen pydantic, как остальной домен.

```python
class Candidate(BaseModel):
    opportunity_id: int
    opportunity: EnrichedOpportunity
    employer: str | None
    freshness: datetime            # posted_at or first_seen_at

class FeedHistory(BaseModel):
    delivered_ids: frozenset[int]  # representatives and their similar_ids
    dismissed_ids: frozenset[int]  # last of dismissed/reopened is dismissed

class Recommendation(BaseModel):
    opportunity_id: int
    score: MatchScore
    rank: int                      # 1-based position in the batch
    similar_ids: tuple[int, ...]   # grouped under this card, best first
```

`src/seawork/recommendation/engine.py`:

```python
def history_from(events: Sequence[BehaviourEvent], delivered: Iterable[int]) -> FeedHistory: ...

def recommend(
    profile: UserProfile,
    candidates: Sequence[Candidate],
    history: FeedHistory,
    *,
    limit: int,
    now: datetime,
) -> list[Recommendation]: ...
```

Порядок внутри `recommend`: исключить историю (§3.3, §3.4) → посчитать `compute_match_score` → исключить `value == 0.0` (§3.5) → отсортировать (§3.6) → сгруппировать (§3.7) → собрать по кругу (§3.8) → обрезать по `limit` и проставить `rank`.

### 4.1 Хранилище

Таблица `deliveries` (миграция `0006`, модель в `storage/models.py`, иначе тесты с `create_all` её не увидят):

| колонка | тип | |
|---|---|---|
| `id` | bigint PK | |
| `user_id` | UUID FK → `user_profiles` ON DELETE CASCADE | |
| `opportunity_id` | int | без FK, как в журнале поведения |
| `similar_ids` | JSONB array of int | `[]`, если группы нет |
| `score_value` | float, null | снимок для аналитики, не истина (`match-score.md` §3.6) |
| `comparable_factors` | int | |
| `channel` | varchar(32) | `telegram` и т.п. — продукт не знает каналов, но аналитике это нужно |
| `delivered_at` | timestamptz | |

Методы — в `ProfileRepository`, рядом с `delete_user` и `export_user`, которые обязаны видеть доставки (решено при реализации 12.10.2026):

- `record_deliveries(user_id, recommendations, channel, delivered_at) -> None` — вся подборка одной транзакцией: доставка, записанная наполовину, оставила бы часть вакансий «показанными», хотя сообщение не ушло;
- `delivered_ids(user_id) -> frozenset[int]` — объединение `opportunity_id` и `similar_ids`;
- `delete_user` удаляет и доставки; `export_user` включает их — это данные о человеке.

Чтение кандидатов — `Repository.list_feed_candidates() -> list[Candidate]` плюс конвертер `OpportunityRecord → EnrichedOpportunity`. Его сейчас нет вовсе (карта, «Главное расхождение»). Колонка `enriched` хранит обогащение без `normalized`, `type` и `quality_*`; их надо собрать из колонок записи. Поля `normalized`, которых в записи нет (`recruitment_office_raw` и др.), на числа оценки не влияют, но фактор `hiring_country` показывает `recruitment_office_raw` как основание — значит, без него объяснение беднее.

**Решено 12.10.2026: не восстанавливаем.** Поле есть только в `raw_items.payload` Pinpoint (`location.name`), и достать его можно лишь повторной нормализацией сырого ответа — на каждое чтение ленты и с парсерами источников внутри хранилища. Цена несоразмерна потере: числа оценки не меняются, страны и нераспознанный регион остаются в `hiring_scope` (регион — дословно, в `unresolved`), пропадает только текст офиса вида «Thailand - Blue Fin» в основании вердикта. Если объяснению он понадобится, сохранять его при ингесте в `enriched`, а не разбирать payload при чтении.

Следствие: `opportunity_fingerprint` кандидата из базы не равен отпечатку той же вакансии при ингесте — шесть полей `normalized` в записи не хранятся. Пока по отпечаткам ничего не кэшируется, это не важно; кэш оценок (`match-score.md` §3.6) обязан брать отпечаток кандидата, а не ингеста.

## 5. Ловушки

- **Слой БД синхронный.** `Session`, а не `AsyncSession`. Бот на async-фреймворке вызывает сервис через `asyncio.to_thread`; переписывать хранилище на async ради бота не нужно.
- **Отпечаток профиля считается на каждую пару.** На 887 кандидатах это 887 sha256 одного и того же профиля — дёшево, но если профилировка покажет, отпечаток считается один раз снаружи. Не оптимизировать заранее.
- **`opportunity_id` без FK** в журнале и в `deliveries`: вакансия может исчезнуть, история остаётся. `delivered_ids` поэтому может содержать id, которых нет среди кандидатов, — это нормально.
- **Работодатель как ключ группы.** У Crewplanet работодатель часто скрыт за крюинговым агентством или пуст — такие записи не группируются (§3.7), и это правильно. Проверить распределение групп на живом корпусе до того, как считать шаг готовым: одна группа на 300 вакансий значит, что ключ слишком грубый.
- **Пустой и неизвестный списки различаются** (`profile.py`): `directions = []` — «сказал, что ничего», ключа нет — «не спрашивали». Для круга по направлениям это не важно, для оценки — важно, не нормализовать.
- **Веса — заглушки** (`weights.py`). Не подкручивать их, чтобы подборка в тестах выглядела красиво.

## 6. Открытые вопросы

1. **Неизвестное против слабого совпадения** (§3.6, п. 1). Ответит E2.1.
2. **Повтор показанного** (§3.4) — после калибровки порога.
3. **Холодный старт без одинаковых подборок** (§3.10) — нужен ли сдвиг по пользователю, решать по первым реакциям.
4. **«Не интересно» по группе.** Отказ от представителя — это отказ от всей группы? В v1 — да, бот пишет `dismissed` на представителя, а участники уже числятся доставленными и так не вернутся.

## 7. Definition of Done

- [ ] `recommend()` чистая: без базы, сети и часов (время — параметр)
- [ ] отклонённое и доставленное не возвращается; `reopened` позже `dismissed` возвращает вакансию
- [ ] `value == 0.0` не возвращается, `value is None` возвращается
- [ ] порядок по §3.6 проверен тестом на каждом уровне ключа
- [ ] группа по (работодатель, профессия) даёт одну карточку с `similar_ids`; запись без одного из полей не группируется
- [ ] в подборке из 5 при кандидатах из трёх направлений нет двух из одного, пока не исчерпаны остальные
- [ ] меньше кандидатов, чем лимит, — короткий список; ноль — пустой
- [ ] `deliveries`: миграция, модель, запись, `delivered_ids`, каскад при удалении, присутствие в выгрузке
- [ ] round-trip на базе: запись → `list_feed_candidates` → `recommend` → `record_deliveries` → повторный вызов не возвращает показанное
- [ ] замер на живом корпусе: доля `None`, размер групп, распределение по направлениям для пустого профиля — записан в журнал плана
- [ ] `ruff`, `pyright`, `pytest`, CI — зелёные
