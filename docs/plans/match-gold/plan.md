# E2.1: эталон пар «профиль × вакансия»
Цель: 30–50 пар с оценкой владельца и команда, которая показывает, насколько текущий Match Score с ней согласен. Это даёт замер, без которого веса нельзя калибровать.
Карта: ./map.md
Спеки: docs/modules/match-score.md (§«Веса», открытые вопросы 1 и 3); docs/roadmap.md E2.1; образец — eval enrichment.
Вне рамок: изменение весов, `_STAGE_LEVELS` и порогов (калибровка — отдельная задача после замера); интересы; LLM.

## Решения
- **Вакансия в эталоне — замороженный `EnrichedOpportunity.model_dump(mode="json")`** с `Candidate.opportunity` из `list_feed_candidates()`, плюс читаемая выжимка (title, employer, описание) для разметки. Эталон не зависит от живой базы. Он замораживает и ошибки обогащения: меряем Match Score поверх данных, какие видит лента, а не идеальных. Это оговорено в шапке файла.
- **Профили пишет архитектор, владелец утверждает.** 8–9 фиксированных профилей, которые покрывают аудиторию спеки (§2): пустой; только этап «присматриваюсь»; новичок с направлением; работающий повар; опытный палубный офицер с сертификатами; инструктор по дайвингу; кандидат с ограничением по стране оформления; кандидат с карьерной целью, отличной от текущей профессии. Без пустого и неполного профиля нельзя измерить `value=None`.
- **Профили двух видов.** Четыре профиля повторяют то, что бот действительно знает о человеке после онбординга: `empty`, `browsing`, `newcomer_cruise` (этап и направления), `onboarded_working` (этап, направления, страна оформления). Остальные описывают будущую аудиторию с профессиями, сертификатами и целью. У нынешних пользователей бота этих полей нет, поэтому замер по таким профилям отвечает на вопрос, как оценка поведёт себя, когда профиль станет полнее. Метрики показываются раздельно по этим двум группам.
- **Отбор пар детерминированный и стратифицирован по текущей оценке.** Страты: `top`, `zero` (0.0 — исключено из выдачи), `low` (наименьшее ненулевое), `middle` (медиана различных значений между low и top), `none`, `random`. Вакансия внутри яруса выбирается с seed, а не по id. Иначе все пары попадут в одну область оценки или в один источник, и порядок проверить будет нечем. Пустая страта ничем не заполняется. У `empty` и `browsing` все оценки `None`, поэтому у них по две пары. Целевой размер — около 44 пар. (Исправлено после ревью шага 2: в исходной версии было «верх, середина, низ» по позиции, и при больших ярусах они совпадали по значению.)
- **Разметка вслепую:** при разметке текущая оценка и факторы не показываются, иначе метка повторит формулу.
- **Метрики** (абсолютный процент не интерпретируется, порога 85% в коде нет):
  - доля правильно упорядоченных пар «подходит» выше «не подходит» внутри профиля;
  - сколько «подходит» получили `value=None` или `0.0`. `0.0` исключает вакансию из выдачи, это самая дорогая ошибка;
  - список расхождений с факторами и caveats, чтобы видеть, какой фактор врёт.
  «Спорно» в бинарные метрики не входит и показывается отдельно.

## Журнал
- 11.11.2026: карта и план написаны.
- 1: 10 профилей, утверждены владельцем (`onboarded_working` добавлен после ревью). Ревью: `certificates: []` у новичка по контракту значит «не имею» и раздувал бы обнуления профилем, которого у бота не бывает, — убрано. Идентичность вакансии читается из дампа, а не из копий рядом; у пары есть `stratum` и `profile_hash`, поэтому метка не устаревает молча при смене профиля. Для шага 2: писатель выводит шапку файла сам (`safe_dump` её теряет); если хеш профиля сменился, старая метка не переносится.
- 2: `seawork eval match sample`. На локальном корпусе 12.10 (810 кандидатов) — 43 пары: top 8, zero 8, low 8, middle 7, none 2, random 10. Ревью: страты по позиции совпадали по значению при больших ярусах, выбор по id тянул все top в один источник — переделано на страты по значению и seed внутри яруса (см. «Решения»). Метки не теряются молча: неизвестный профиль у размеченной пары — ошибка до записи, снятие меток при смене хеша — только с `--drop-stale`. `None` у профилей с фактами не встречается вовсе: хотя бы один фактор всегда сравним. Для шага 4: `eval match` стал группой — команда отчёта будет подкомандой (`eval match report`), а не `eval match <file>`.
- 3: `seawork eval match label`. Файл отсортирован по профилю и страте, поэтому показ по порядку выдавал страту (первая пара профиля всегда top) — пары показываются в детерминированно перемешанном порядке, ключ от самой пары. Описание обрезается по слову на 1500 символах: требования обычно в конце. Сменившийся `profile_hash` останавливает разметку до первой пары. Ctrl+C сохраняет всё размеченное.
- 4: `seawork eval match report [--log]`. Ревью: в исходной версии пары страты zero (почти все будут «не подходит») раздували долю порядка тривиальными победами, а ничьи по value съезжали к 50%, хотя выдача разводит их по числу сравнимых факторов. Теперь порядок считается только между парами, которые обе в выдаче, по ключу `rank_tier` из движка (выделен отдельным коммитом). Ничья — полное равенство ключа. Исключение из выдачи — отдельная метрика (верное и ошибочное). Группа профиля (`kind`) и структурный None (`structural_none`) заданы в профилях, хеш считается только по фактам. Эталон шага 5 уже отобран (43 пары) — правки формата его не затронули.
